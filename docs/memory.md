# メモリ最適化（2026-09-07）

解析・逆アセンブルを1つの JVM と処理キューにまとめた。実行用 JVM は分離し、実行終了時に終了する。構文検証、フレーム・グラフ生成、標準ライブラリは削除していない。

## 自動設定

`navigator.deviceMemory` は搭載量の概算であり、空き容量ではない。取得できない場合や不正値の場合は通常設定を使う。大量搭載マシンでも割り当てを際限なく増やさない。

| 設定 | 通常・容量不明 | 容量の目安が4 GiB以下 |
| --- | ---: | ---: |
| 解析・逆アセンブルの Java ヒープ | 64 MiB | 32 MiB |
| 実行用 Java ヒープ | 128 MiB | 64 MiB |
| 使用例のキャッシュ | 最近使った24件 | 最近使った8件 |
| バックグラウンドでの解析 JVM 解放待ち | 60秒 | 30秒 |

解放待ちは最後の処理が終わってから数える。処理中・待ち行列にあるジョブは停止しない。画面に戻れば解放待ちを取り消す。ブラウザのタイマー抑制により、実際の解放時刻は遅れることがある。

解放時もソース、表示状態、保存済みの解析結果は維持する。キャッシュで回答できる操作は再起動せず、新しい解析や逆アセンブルが必要なときだけ JVM を再起動する。再起動には待ち時間がかかる。

## 測定

Windows / Edge 152 headless、本番ビルド、空のブラウザコンテキスト。各設定1回の状態別測定。以下はアプリを表示する描画プロセスで、Workerを含み、ブラウザ本体・GPU・予備プロセスは除く。

JSヒープはGC後の値。WASMは`WebAssembly.Memory.buffer.byteLength`で領域容量を測る。Windowsの常駐量とプライベートコミット量はそれぞれ別の指標であり、WASM容量と足し合わせない。

| 状態 | 変更前 常駐 / 確保 | 通常 常駐 / 確保 | 省メモリ 常駐 / 確保 |
| --- | ---: | ---: | ---: |
| 初期解析後 | 356.9 / 467.4 MiB | 357.1 / 357.2 MiB | 358.5 / 352.2 MiB |
| Instructions / Graph 表示後 | 382.1 / 491.5 MiB | 382.9 / 381.0 MiB | 384.9 / 377.6 MiB |
| 実行中 | 556.0 / 817.2 MiB | 556.5 / 706.3 MiB | 560.6 / 656.8 MiB |
| 実行終了後 | 389.9 / 498.8 MiB | 392.3 / 386.9 MiB | 394.4 / 384.0 MiB |
| バックグラウンドで解放後 | 未測定 | 178.5 / 113.5 MiB | 181.1 / 115.2 MiB |

通常設定の解析用WASM領域は372.6 → 262.1 MiB、省メモリ設定では258.0 MiB。実行中は通常572.6 MiB、省メモリ520.1 MiBで、実行終了後は解析用1台に戻る。待機解放後はWASM領域がなくなる。

**起動直後の実際の常駐量はほぼ変わらず、主に確保量を削減した。** 常駐量が大きく下がるのは、待機中のJVMを終了したとき。32 MiBと64 MiBの解析ヒープでは、この測定の常駐量に有意な差は確認できなかった。

逆アセンブルやSystem.outへの定義ジャンプ後も解析用Workerは1台のままであることをブラウザテストで確認した。メモリ表の「実行中」はThread.sleep中の1点で、あらゆるプログラムの最大使用量を示すものではない。

## 確認した機能

- 32 MiB解析ヒープで202命令すべての使用例がコンパイルでき、ホバー用フレームが取得できる。
- 両設定で1,001命令の解析、classのD&D、標準ライブラリへの定義ジャンプ、Hello Worldの3回実行が成功する。
- バックグラウンド解放後もキャッシュは使え、新しい解析ではWorkerが再起動する。
- 共有キューの直列実行・失敗後の復旧・実行中の解放防止、使用例キャッシュのLRUを単体テストで確認。
- メイン画面・小窓のGraph、Console、Problemsの回帰テストと本番ビルドが成功。

小さいJavaヒープではGC増加や、大きいプログラムのメモリ不足が起こり得る。任意のプログラムについて同じ動作・性能を保証する設定ではない。実行は副作用を重複させないよう、自動リトライしない。

## 解析速度

同じBovine・同じRuntime実装で、初期化後に128 → 64 → 64 → 128 MiBの順に独立したJVMを使い、各入力を解析した。UIの処理は含めない。

| 入力 | 128 MiB（2回の中央値） | 64 MiB（2回の中央値） |
| --- | ---: | ---: |
| 21命令 | 325.3 ms | 262.6 ms |
| 201命令 | 2,318.0 ms | 2,250.7 ms |
| 1,001命令 | 14,497.3 ms | 15,172.1 ms |

大きな入力では約4.7%遅い結果だった。128 MiBの2回も13.3秒と15.7秒の幅があり、この少数回の測定だけで厳密な差は断定しない。通常設定は確保量を抑える64 MiBとした。`node scripts/compare-heap-performance.mjs`で交互測定を再実行できる（5225番ポート）。

## 再測定

```powershell
npm.cmd run build
node scripts/measure-memory.mjs .cache/memory-normal.json
$env:JALWEB_DEVICE_MEMORY='4'
node scripts/measure-memory.mjs .cache/memory-low.json
Remove-Item Env:JALWEB_DEVICE_MEMORY
node scripts/measure-performance.mjs .cache/performance-memory.json
```

メモリ測定はWindows専用で5223番ポート、速度測定は5222番ポートを使用する。他のビルド・ブラウザテストとは同時に実行しない。メモリ測定では処理がない状態の解放タイマーだけを短縮し、`visibilitychange`を送って解放と再開を測っている。ブラウザが非表示ページを凍結する挙動は測っていない。

## 表示データと配置のキャッシュ

通常の検査・ビルドでは診断と class のみを生成する。ホバーと Instructions の使用例はフレーム表示データ、Graph はグラフデータを要求する。どのモードでも LangJAL と ASM の型検証は行う。要求が増えた場合は不足した結果を生成し、同じソースの上位の結果は共有する。待機中の要求は統合する。

グラフはソース内容、配置はメソッドの表示内容と接続関係（フィルター適用後）で再利用する。配置を再利用してもノード ID・行・列・到達可能性は現在の解析結果から更新する。最近のファイルに戻った場合は構文解析と ELK 配置を省略できる。DOM は保持せず作り直す。

解析結果・ファイルのグラフ・メソッド配置にそれぞれ容量制限付き LRU を使う。`deviceMemory` が 4 GiB 以下または不明なら各 4 MiB、それより大きければ各 16 MiB を目安とする。件数上限もそれぞれ 64 文書・16 ソース・256 メソッドとする。サイズは文字列化したデータ量に係数を掛けた保守的な推定で、実ヒープ使用量の上限ではない。画面が現在利用しているデータや JVM、ブラウザ本体は別になる。

`deviceMemory` は端末容量の粗い情報であり、空き RAM の測定ではない。上限を超えた古い結果は破棄し、必要になったら再計算する。小窓の配置キャッシュは窓ごと、コンパイルのキャッシュは親のサービスで共有する。永続化はしない。上のメモリ・速度表はこの変更以前の測定値である。
