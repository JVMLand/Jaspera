# 構文解析の測定

2026-09-08，Windows / Node.js v22.14.0。OpenJDK 23 から逆アセンブルしたソースを使用した。ウォームアップ後9回の中央値。ブラウザの JavaScript Worker と同じ解析コードを Node.js で実行した値であり，ブラウザ実測や JVM の型・フロー解析時間ではない。

| 対象 | 文字数 | 従来の3回解析 | 高速予測＋1回共有 |
| --- | ---: | ---: | ---: |
| PrintStream | 44,849 | 2,171.44 ms | 8.37 ms |
| String | 128,261 | 11,339.80 ms | 39.69 ms |

従来の LL のまま1回共有した場合は，それぞれ 1,064.87 ms / 4,049.68 ms。同じ高速予測でも3回別々に解析すると 20.21 ms / 84.57 ms だった。数字は同一マシンの参考値で，測定中のCPU負荷やJIT・GCの影響を含む。

ANTLR の SLL と BailErrorStrategy で先に解析し，完了できなければ，同じ字句列を先頭に戻して従来の LL とエラー回復を使う。文法や検証を省略しない。PrintStream / String では LL とオフセット・検査・引数番号の全結果を比較した。入力途中や不正文字の回帰テストも含む。

オフセット・検査・引数番号は1リクエスト内の構文木を共有する。マクロ展開でソースが変わる場合のみ別の構文木になる。リクエストをまたいで構文木は保持しない。定義検索・グラフのメソッド一覧・フォーマッタにも同じパーサーを使う。

測定の再実行：

```sh
node scripts/measure-source-parsing.mjs
# JDKラウンドトリップのテストで生成したソースがある場合
node scripts/measure-source-parsing.mjs --compare-ll .cache/jdk-roundtrip/PrintStream.jal .cache/jdk-roundtrip/String.jal
```

通常出力は高速予測によるパーサー単体・3回別々・1回共有の中央値。`--compare-ll` は追加で従来の LL による1回共有の実行時間を測り，結果の一致を検証する。この追加値は1回の測定で，表の9回中央値とは条件が異なる。

Java/WASM 側のコンパイラと型・フロー解析は今回変更していない。グラフが完成するまでの時間全体が表と同じ比率で短くなるわけではない。

## Graph 側の追加改善

Java/WASM 側にも SLL と LL フォールバックを導入した。構文解析中は読み終えたメソッドの終端トークン位置から進捗を通知する。通知は最大約10回/秒と開始・終了時。百分率は構文解析のソース消化率で，Graph全体の完了率や残り時間ではない。

ネイティブJavaで字句解析を含む構文解析を9回測定した中央値：PrintStream 69.63→0.91 ms，String 450.46→3.59 ms。JavaScript側の上表とは別の測定。

同じ既存のブラウザJVMテスト（逆アセンブル・コンパイル・フレーム・グラフ情報生成）では，String 16,826 ms，HashMap 6,788 ms，Integer 5,674 ms。前回記録はそれぞれ81,843 / 33,064 / 25,804 msだった。単一実行の参考値であり，SVGの配置・描画時間は含まない。
